### Fixed

- **`save_artifact` keeps the mode and group of the file it replaces** — a save over a file with mode `0640` in a supplementary group gave the new file the umask mode and the user's primary group, because the tmp file was a new inode. The payload is now published through `dokimi.atomic_write.write_bytes_in_place_or_atomic`: a plain file is replaced by rename and keeps its mode and, where the user may give it, its group; a read-only file in a writable directory is replaced by rename as before (except on Windows, whose `os.replace` refuses a read-only destination: there it is written in place and refused, and `tools preference` exits 2 before any probe call) and now stays read-only, also when it has another hard link, a `user.*` attribute, an ACL or another owner, which the new file does not keep; a new file still gets the umask mode; a writable hard-linked or other special file, or a file in a read-only directory, is written in place, as `Path.write_bytes` writes it; a symlink at the path stays and the file it resolves to is replaced. An in-place write is not atomic (a reader can see a partial file), and a file the user cannot write in place raises `PermissionError`. A file replaced by rename gets no access ACL from its directory's default ACL, and another user's read-only file in a sticky directory (which `os.replace` refuses) is written in place and refused. `tools preference` checks `--out` the way the save will write it: a writable file in a read-only directory and a long file name are accepted, a read-only file in a read-only directory is refused with exit 2 before any probe call.
