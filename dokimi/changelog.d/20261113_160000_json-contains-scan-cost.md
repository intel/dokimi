### Fixed

- **`parse_json(contains=True)` no longer costs starts x text length** — the scan was capped at 1000 `{` or `[` tries, but each try on a long text parsed the whole tail before it failed, so `'[' * 900 + '1,' * 100000` took seconds to read as not JSON. The tries that fail now share a budget of 1,000,000 scanned characters (`CONTAINS_JSON_MAX_SCAN`; a try that fails without a position, or on an unterminated string, is charged to the end of the text; the first parse of the whole text is not counted), and the scan reads the text as not JSON once it is spent (failed tries that have scanned exactly 1,000,000 characters have spent it; one try may cross it), as it does at the start cap. A value found after failed tries that scan under the budget in all, and a value of any length when no earlier try failed late, are found as before; a few failed tries are enough to spend it when each reads a long tail. A check whose scan gives up fails as `not JSON`, it is not left unscored as a `regex` check past its limit is: `'[' * 6 + '1,' * 100000 + ' {"a": 1}'` (six tries of 200,000 characters each) found the object before this change and fails now. The same holds for a value before a long run of brackets: a try that hits the depth limit reports no position, so it is charged the rest of the text, and `'[' + '{"a": 1},' + '[' * 1_100_000` reads as not JSON where it found the object before.
